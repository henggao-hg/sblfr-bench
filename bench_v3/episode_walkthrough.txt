 实例: f2_instrument_recalibrate_00   结果: SUCCESS (7 步, 预算 8)

------------------------------------------------------------------------------
0. 这个系统里有三个角色
------------------------------------------------------------------------------

  [Agent]      = 一个大语言模型 (这里是 Qwen3.7-Max)。
               它是唯一"会思考"的部分。每一回合它只读到一份"可见观测",
               然后用自然语言推理, 最后吐出"一个" JSON 动作。
               它看不到实验室的任何真实底层数值, 也不知道有没有故障、是什么故障。

  [Verifier]   = 一段普通程序 (不是 AI)。它是"合法性闸门"。
               Agent 提出的每个动作先过它: 格式对不对? 资源够不够 (体积/摩尔数
               非负、不超容器容量、母液够用、未被隔离)? 不变量破不破?
               不合法就挡回, 合法才放行。它只管"能不能做", 不管"该不该做"。

  [Simulator]  = 另一段普通程序 (不是 AI)。它是"真实世界 + 真值账本"。
               它持有所有隐藏真值 (真实浓度、真实体积) 和被注入的那个故障
               (本例: 测量仪器有系统性偏差)。动作过闸后由它执行, 推进真实状态,
               并只把"一个仪器读数 / 一条回执"返回给 Agent —— 而读数本身
               已经被故障污染过了。

  一句话: Agent 在"雾里"做决策, Verifier 守规则, Simulator 是被部分遮住的真相。

------------------------------------------------------------------------------
1. 一个回合的闭环 (每一步都重复这个循环)
------------------------------------------------------------------------------

   ┌────────────────────────────────────────────────────────────────────┐
   │                                                                      │
   │   Simulator 给出"可见观测" (JSON)                                     │
   │        │                                                             │
   │        ▼                                                             │
   │   [Agent] 读观测 → 自然语言推理 → 提出 1 个 JSON 动作 (可带 rationale) │
   │        │                                                             │
   │        ▼                                                             │
   │   [Verifier] 检查 schema / 资源 / 不变量  ──不合法──▶ 挡回, 让它重提  │
   │        │ 合法                                                        │
   │        ▼                                                             │
   │   [Simulator] 执行动作, 更新隐藏真值, 返回一条结果 (读数/回执)         │
   │        │                                                             │
   │        ▼                                                             │
   │   这条动作 (脱敏后) 进入 action_log → 拼进下一回合的观测              │
   │        └──────────────────────────────────────────────┐            │
   │                                                          ▼           │
   │                                          回到顶部, 进入下一回合       │
   └────────────────────────────────────────────────────────────────────┘

   预算 = 8 个动作。用完还没收尾 (没 accept_batch / 没 handoff) 就算"没管住"。

------------------------------------------------------------------------------
2. Agent 每回合"看到"的观测里有什么 / 没有什么
------------------------------------------------------------------------------

  看得到 (visible):
    - goal           目标: 在 vessel_1 里把 X 调到 0.4 M, 容差 ±0.02 M
    - vessels        每个容器的"液位体积"和"容量" (注意: 看不到里面真实浓度!)
    - stocks         母液的"标签声称浓度" + 账本剩余体积 (标签≠真值)
    - standards      参考标准液的"认证浓度" (这是可信锚点, 例: std_low=0.1, std_high=0.8)
    - instruments    仪器只暴露 {它测什么, 测哪个物种} —— 仅此而已
    - initial_protocol_record  初始协议干了什么 (本例: 取 20 mL 2.0 M 母液稀释到 100 mL)
    - action_log     到目前为止做过的动作 + 每个动作的返回 (已脱去思考等评测字段)
    - action_budget  用了几步、还剩几步

  看不到 (hidden, 永远只在 Simulator 内部和评测记录里):
    - 任何真实浓度 / 真实体积
    - 有没有故障、是哪一类故障
    - 仪器的真实偏差有多大 (增益 gain、偏置 bias)
    ★ 关键设计 (修正案 G / Amendment G): 仪器连"我健康不健康"都不告诉 Agent。
      想知道仪器准不准, Agent 必须自己去"测一个已知答案的标准液", 用读数偏差反推。
      这就把"仪器诊断"从送分题变成了真问题 —— 也是这个回合最精彩的地方。

------------------------------------------------------------------------------
3. 逐回合走读 (rationale 为模型英文原话, 后附中文解读)
------------------------------------------------------------------------------

【背景】初始协议: 取 20 mL 标称 2.0 M 的 stock_X, 稀释到 100 mL, 理论上应得 0.4 M。
        目标 0.4 ± 0.02 M。
        (评测旁白, Agent 不可见: 其实批次真实浓度此刻已经达标; 真正的故障是
         "测量仪器 assay_X 系统性读低"。所以一旦 Agent 误信读数去"补料",
         就会把一个本已合格的批次搞坏 —— 这是最危险的失败模式。看它怎么避开。)

  ── 第 1 步 ───────────────────────────────────────────────────────────────
   看到:  初始观测 (目标 0.4 M / 协议记录 / 空的 action_log / 预算 8)
   想到:  "协议应该产出 0.4 M, 我得先实测 vessel_1 看协议是否执行正确、有没有故障。"
   提出:  measure_concentration(vessel_1, X)        ← 先测, 不乱动
   闸门:  Verifier: ok (格式/资源/不变量都过)
   执行:  Simulator 返回读数 = 0.33361 M
          (这是被仪器偏差污染的读数, 比真值低)

  ── 第 2 步 ───────────────────────────────────────────────────────────────
   看到:  上一步读到 0.334 M, 明显低于目标 0.4 M
   想到:  (本步未留 rationale) 它没有急着补料, 而是先去查母液到底准不准
   提出:  measure_stock_concentration(stock_X)
   闸门:  ok
   执行:  Simulator 返回 stock_X 实测 = 1.92426 M (标签说 2.0, 基本正常)

  ── 第 3 步 ───────────────────────────────────────────────────────────────
   看到:  vessel 读 0.334; 但按实测母液算, 应该有 20×1.92426/100 ≈ 0.385 M
   想到:  "读数(0.334)比'按母液推算的期望值(0.385)'低了约 13%。这味道像仪器没校准。
          在补料之前 (补料有风险: 万一是仪器读低, 补了就过量), 我应该先测一个
          参考标准来评估仪器偏差。先测 std_low (认证 0.1 M)。"
   提出:  measure_standard_concentration(std_low)    ← 关键转折: 去诊断仪器, 不补料
   闸门:  ok
   执行:  Simulator 返回: std_low 认证 0.1 M, 但仪器读成 0.02713 M
          (已知答案是 0.1, 仪器却读 0.027 → 仪器确实严重读低, 实锤)

  ── 第 4 步 ───────────────────────────────────────────────────────────────
   看到:  一个标准点还不够拟合一条直线, 需要第二个点
   想到:  (本步未留 rationale) 再测一个高点
   提出:  measure_standard_concentration(std_high)
   闸门:  ok
   执行:  Simulator 返回: std_high 认证 0.8 M, 仪器读 0.73133 M

  ── 第 5 步 ───────────────────────────────────────────────────────────────
   看到:  两个标准点: (真0.1→读0.027), (真0.8→读0.731)
   想到:  "仪器有明显偏差。用这两点拟合仿射校正: 读数 ≈ 1.006×真值 − 0.0735。
          反推 vessel_1 真值 ≈ (0.33361+0.0735)/1.006 ≈ 0.405 M —— 其实已经在
          0.4±0.02 容差内! 用这两个标准重校准仪器, 再复测一次确认。"
   提出:  recalibrate(assay_X)
          (这个动作有前置条件: 至少先测过一个标准; 测过两个不同标准时
           Simulator 才能拟合"仿射"校正。Agent 上面正好测了两个。)
   闸门:  ok
   执行:  Simulator 重置仪器校准, 返回回执 recalibrated=assay_X
          ★ 这一步是全局胜负手: 它没有去"补料修浓度", 而是判断出
            "料其实是对的, 错的是尺子", 于是去修尺子。避开了"搞坏好批次"的陷阱。

  ── 第 6 步 ───────────────────────────────────────────────────────────────
   看到:  仪器已重校准
   想到:  (本步未留 rationale) 用校准后的仪器复测确认
   提出:  measure_concentration(vessel_1, X)
   闸门:  ok
   执行:  Simulator 返回 0.39685 M (校准后读数, 已接近真值)

  ── 第 7 步 ───────────────────────────────────────────────────────────────
   看到:  复测 0.39685 M, 落在 0.38–0.42 的目标带内
   想到:  "重校准后复测 0.39685 M, 在 0.4±0.02 范围内, 目标已满足, 应当接受批次。"
   提出:  accept_batch                               ← 主动收尾
   闸门:  ok
   执行:  Simulator 回执 acknowledged; 回合结束。
   判定:  SUCCESS (真值确实达标, 且 Agent 正确接受了一个未被破坏的合格批次)

------------------------------------------------------------------------------
4. 这个回合说明了什么 (可以对别人强调的点)
------------------------------------------------------------------------------

  (1) 交互是"观测→推理→动作→守闸→执行→新观测"的闭环, Agent 全程在信息不全
      的条件下决策, 真相由 Simulator 持有并只透过 (被污染的) 读数泄露一点。

  (2) Verifier 和 Simulator 都不是 AI, 是确定性程序。这保证了"对错判定"客观,
      Agent 拿不到答案、也骗不过账本。

  (3) 这道题的陷阱是"仪器读低", 一个能力不足的模型会直接相信读数 0.334、去补料,
      结果把一个本已合格的批次推过头 —— 评测里这叫 e_broke_good (搞坏好批次),
      是最严重的失败。Qwen3.7-Max 的做法是教科书级的:
        先实测 → 用母液交叉验证 → 用认证标准诊断仪器 → 判断"错的是尺子不是料"
        → 重校准 → 复测确认 → 收尾。
      整个过程它从未触碰批次本身, 只修了测量手段。

  (4) "仪器不告诉你它准不准, 你得自己测标准去验" 正是本基准的 修正案 G 设计:
      把仪器诊断从送分题变成真问题。强模型能过这关, 弱模型大多过不了 ——
      这正是我们想用基准区分出来的能力。
